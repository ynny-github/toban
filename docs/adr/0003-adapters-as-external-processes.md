# custom の Tracker と Executor は外部コマンドの Adapter として差し込み、組み込みのものは本体内で動かす

Tracker と Executor を本体の中のインターフェースとして実装するだけだと、ユーザーは自分のトラッカーや実行側をつなぐのに本体の対応を待つしかない。そこで、操作ごとにコマンドを起動して JSON を受け渡すコマンドフックを公開のプロトコルとし、任意の言語で custom の Adapter を書けるようにする。オーケストレータは worker を起動したら手を離すので、Executor に頼むのは「この Issue とプロンプトで worker を起動する」だけであり、常駐プロセスとの双方向の通信は要らない。組み込みの Adapter（GitHub、Orca）は本体内で Go のインターフェースを直接実装し、プロトコルを通さない。custom が組み込みと同じことをすべてできる必要はない。

最初のリリースには custom の Adapter もプロトコルも入れず、組み込みの GitHub と Orca だけを提供する。ただし本体は Go のインターフェースにだけ依存させ、その引数と戻り値は JSON に変換できる型に限って、後からプロトコル経由の実装を足せる形にしておく。

## Considered Options

- **本体内のインターフェースのみ**：最も単純だが、上の理由で採らなかった。
- **Executor は常駐する子プロセスと stdio の JSON-RPC で話す**：worker のイベントを受け取るなら必要だったが、監督をやめたため採らなかった。
- **組み込みも同じプロトコルで子プロセスとして動かす**：プロトコルの不足がすぐ表に出るが、組み込み側の開発・調査の手間が増える。custom と組み込みの完全な一致は求めないため採らなかった。
- **Go プラグイン（hashicorp/go-plugin, gRPC）**：型安全だが、実質 Go でしか書けず自由度が上がらないため採らなかった。

## Consequences

- プロトコル（JSON の形と呼び出し順）が公開 API になり、互換性を保つ責任が生じる。
- Adapter の異常終了、壊れた出力、タイムアウトを本体が扱う必要がある。
